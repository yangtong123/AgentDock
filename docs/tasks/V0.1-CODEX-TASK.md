# V0.1 Codex Task — Core Foundation

## Objective

Implement **AgentDock V0.1 — Core Foundation** only.

This milestone establishes the project skeleton, durable domain model, SQLite persistence, migrations, repository/service boundaries, and a minimal local CLI. It must intentionally avoid implementing future-version runtime integrations.

Read `AGENTS.md` and `docs/ROADMAP.md` before making changes.

## Technology

Use:
- Node.js
- TypeScript
- SQLite

Prefer a minimal dependency set. Choose a currently supported Node.js baseline and document it in the README/package metadata.

## Required project structure

Use a modular structure approximately like:

```text
src/
  app/
  db/
  projects/
  tasks/
  workflows/
  agents/
  artifacts/
  shared/

migrations/
tests/
```

Exact filenames may differ if there is a clear reason, but domain boundaries must remain explicit.

## Required domain entities

### Project

Represents a managed source repository.

Minimum fields:
- id
- name
- repoPath
- baseBranch
- worktreeRoot
- status: ACTIVE | PAUSED | DISABLED
- maxConcurrentTasks
- defaultWorkflowPreset (nullable)
- createdAt
- updatedAt

### Task

Represents durable user intent and task lifecycle metadata.

Minimum fields:
- id
- projectId
- state
- currentRevision
- branch (nullable)
- worktreePath (nullable)
- createdAt
- updatedAt

Do not store mutable request text directly on Task.

### TaskRevision

Requirements are versioned.

Minimum fields:
- id
- taskId
- revision
- request
- createdAt

Creating changed requirements later must be representable as a new revision without overwriting prior requirements.

### WorkflowRun

Represents one execution attempt for a TaskRevision.

V0.1 only needs persistence/domain representation; do not execute workflows yet.

### StepRun

Represents one workflow step execution.

Prepare types for:
- PLAN
- IMPLEMENT
- VERIFY
- REVIEW
- FIX
- FINAL_REVIEW
- HUMAN_APPROVAL

Prepare lifecycle state for:
- QUEUED
- RUNNING
- SUCCEEDED
- FAILED
- CANCEL_REQUESTED
- CANCELLED

V0.1 must not implement actual agent execution.

### AgentThread

Represents a provider-specific conversation/thread associated with a task.

Minimum fields:
- id
- taskId
- provider
- role
- externalSessionId (nullable)
- createdAt
- updatedAt

Do not put `claudeSessionId` or `codexSessionId` directly on Task.

### Artifact

Represents durable output from workflow steps.

Design it so later versions can store/reference items such as:
- request.md
- plan.json / plan.md
- review.json / review.md
- verify.json / verify.log
- diff.patch
- agent stdout/stderr

Do not implement agent-generated artifacts yet beyond the persistence abstraction needed for V0.1.

## Persistence

Use SQLite with explicit migrations.

Requirements:
- migrations run safely on application startup or through a documented command
- foreign keys are enabled
- database directory is created safely when appropriate
- repositories encapsulate SQL access
- domain/application services do not scatter raw SQL throughout the codebase
- persistence survives process restart

Do not add Redis or another external database.

## Repository/service boundaries

At minimum provide clean persistence/service boundaries for:
- ProjectRepository
- TaskRepository
- WorkflowRepository (or equivalent split for WorkflowRun/StepRun)
- AgentThreadRepository
- ArtifactRepository

Services should own domain operations such as creating a project and creating a task with its initial TaskRevision.

Keep external adapters out of core domain logic.

## Minimal local CLI

Add a small development/operator CLI sufficient to prove V0.1.

Required capabilities:
- add/create a Project
- list Projects
- create a Task in a Project with an initial request/revision
- list Tasks
- show one Task including its current revision

The exact command syntax is up to the implementation, but it must be documented and easy to run.

## Tests

Add automated tests covering at least:
- migrations on a clean database
- creating and reading a Project
- creating a Task and initial TaskRevision atomically/consistently
- requirement revisions do not overwrite earlier revisions
- persistence survives reopening the database
- important foreign-key/domain constraints

Favor domain/repository tests over superficial snapshot tests.

## Documentation

Update README with:
- what AgentDock is
- current V0.1 status
- prerequisites
- install commands
- development commands
- migration/database usage
- local CLI examples
- test command
- explicit note that agents/worktrees/Telegram/Feishu/GitHub are future milestones

## Explicit non-goals for V0.1

Do NOT implement:
- Codex CLI/SDK integration
- Claude Code CLI/SDK integration
- ProcessRunner for coding agents
- Git worktree creation
- workflow execution
- Telegram
- Feishu/Lark
- GitHub PR integration
- worker scheduler
- leases/heartbeats
- outbox notifications
- production deployment
- Redis
- Kubernetes
- web dashboard

Interfaces that make future work clean are welcome, but avoid speculative framework-building.

## Acceptance criteria

A reviewer must be able to:

1. install dependencies
2. run migrations/start the app against a fresh SQLite database
3. create at least two Projects
4. create Tasks in different Projects
5. create a second revision for a Task without losing revision 1
6. stop the process
7. restart/reopen the same database
8. list the same Projects/Tasks/revisions successfully
9. run the test suite successfully
10. inspect a codebase where core domain logic is not coupled to Telegram, Feishu, GitHub, Claude, or Codex
