# V1.1 Task — Cross-Agent Workbench

## Status

In progress. This document defines the first post-V1.0 product milestone. It does not change the V1.0 runtime or release contract.

- Milestone 1 (Local Gateway and Activity Stream): implemented — `src/gateway/` (REST + SSE, token auth, idempotency), `src/activity/` (durable activity events), `src/commands/` (shared CLI/IM/HTTP command handlers), migration `012_activity_events.sql`.
- Milestone 2 (Read-Only Desktop Workbench): implemented — `workbench/` (React + TypeScript + Vite, served statically by the gateway), project/task list with attention badges, run detail (step timeline, virtualized live logs via byte-offset tailing, verification vs review sections, structured findings, per-file diff, artifacts, revisions, activity timeline), SSE-driven live updates, URL-restored views (`/tasks/:id`).
- Milestone 3 (Task Composer and Desktop Controls): implemented — task composer (project, requirement, preset, per-step provider assignment with quick combos, max review rounds, permission-profile display, scheduling/priority), run controls (prepare/start/approve/reject/cancel/retry/revise/swap-and-rerun), per-intent idempotency keys with replay-on-retry, optional `expectedRunState` conflict guard on run mutations, 409-conflict → refetch UX.
- Milestone 4 (Cross-Channel Continuity): implemented — IM `/run` accepts per-step provider assignments, `/providers` command, all IM mutations route through the shared command layer with normalized actors (`telegram`/`feishu`; conversation id in detail), approval-request/terminal/cancellation/timeout notifications delivered per subscribed conversation (Telegram and Feishu identities never crossed; no broadcast fallback), contract + concurrency tests (`tests/contract.test.ts`). - Milestone 5 (Security, Stability, and Release): code-complete — CI matrix, secret-redaction sentinel, SSE slow-client/cursor tests, full deterministic suites green (see `docs/tasks/v1.1-release-checklist.md`). **All real-environment acceptance passed on 2026-08-19**: a single-provider run (All Claude), both Claude×Codex directions (tasks `68759d8a`/`6fde9a7c`), and cross-channel continuity in both directions — desktop-started `careful` run approved from Feishu (task `b7b284cb`, both gates; the second auto-notified) and a Feishu-started run observed live on desktop (task `0717432b`, actor recorded as `feishu`). codex ran on a standalone CLI install (0.148.0) with a DeepSeek provider. Known acceptance finding: a desktop-started task notifies no IM conversation until first IM interaction (subscription model) — its first approval gate is workbench-only. Remaining: release mechanics (commit, CI green on main, README quick-start verification).

## Objective

Turn AgentDock from a CLI/IM-operated orchestrator into a task-centric, interactive coding-agent workbench.

The primary workflow is:

1. Start a development task from a desktop browser or a phone IM.
2. Assign Claude or Codex to implement it.
3. Assign the other provider to review it.
4. Observe verification, findings, fixes, and approval gates in real time.
5. Continue, approve, reject, revise, or stop the same durable task from either surface.

Provider and role remain independent. Both of these combinations are first-class:

- Claude implements, Codex reviews.
- Codex implements, Claude reviews.

The desktop workbench and Telegram/Feishu are two control surfaces over the same AgentDock `Task`, `TaskRevision`, `WorkflowRun`, and `StepRun`. They must not create separate task histories or execution paths.

## Product decisions

### Local web workbench first

V1.1 adds a browser-based workbench served by the local AgentDock process. It must bind to `127.0.0.1` by default.

A Tauri/Electron wrapper is deferred. A local web UI delivers the desktop workflow with less packaging, update, signing, and cross-platform work. The backend and UI boundaries should allow a native wrapper later without changing domain commands.

### Task interaction, not generic chat

V1.1 is an interactive development workbench, not a general-purpose multi-agent chat client.

Interaction is attached to durable work:

- start a task;
- inspect progress and output;
- approve or reject a gate;
- add a follow-up instruction as a new `TaskRevision`;
- rerun a failed workflow;
- switch implementer/reviewer assignments for a new run;
- cancel active work.

Free-form direct chat, arbitrary agent rooms, and ephemeral conversations are out of scope.

### Fixed workflows before a workflow builder

V1.1 exposes the existing `fast`, `cross-review`, `careful`, and `fix` presets plus per-step provider assignment. It does not add a visual DAG editor, automatic complexity routing, or agent-selected global workflow changes.

### One command authority

The top-level orchestrator remains the only execution authority. The web UI and IM adapters may request commands, but they must not:

- execute agents directly;
- mutate SQLite directly;
- dequeue tasks or acquire leases independently;
- bypass project state, scheduling, concurrency, timeout, approval, or sandbox rules;
- construct shell commands from user input.

## Scope

V1.1 includes:

- a local HTTP gateway over AgentDock application services;
- a server-sent event stream for live task updates;
- a desktop workbench for projects, tasks, runs, steps, logs, findings, diffs, and artifacts;
- a task composer with explicit workflow and provider assignment;
- desktop commands for start, approve, reject, stop, revise, and rerun;
- consistent cross-channel state and notifications between desktop, Telegram, and Feishu;
- security, reconnect, concurrency, and end-to-end coverage for the new surface.

## Non-goals

Do not implement the following in V1.1:

- native desktop packaging;
- a native mobile app;
- cloud hosting or remote internet exposure;
- multi-user accounts, team RBAC, or multi-tenancy;
- multi-machine workers;
- Slack, Discord, or additional IM adapters;
- a visual workflow/DAG builder;
- automatic provider or complexity routing;
- generic direct chat with Claude/Codex;
- attachment management;
- MCP server, skill, or prompt marketplace management;
- GitHub auto-merge;
- new coding-agent providers unless a small provider-neutral interface fix is required.

## Architecture

```text
Local browser workbench ----+
                            |
Telegram / Feishu ----------+--> Local Gateway --> Application commands
                                   |                    |
                                   |                    +--> Workflow Engine
                              REST commands             +--> Orchestrator
                              SSE events                +--> Claude / Codex
                                   |                    +--> Worktree / Git
                                   |                    +--> SQLite / Artifacts
                                   |
                                   +--> Read projections built from durable state
```

### Boundaries

1. Existing application/domain services own commands.
2. The orchestrator owns queue claims, leases, concurrency, heartbeats, cancellation, timeouts, recovery, and workflow execution.
3. SQLite, Git state, and artifacts remain the source of truth.
4. The browser state is a projection. A refresh or reconnect must rebuild it from the gateway.
5. Structured activity events provide ordering and reconnect cursors, but do not replace authoritative domain tables.
6. High-frequency stdout/stderr chunks must not become unbounded SQLite rows.
7. Every mutating command records the actor source: `desktop`, `telegram`, `feishu`, `cli`, or `system`.

### Proposed module boundaries

The exact filenames may change, but the dependency direction must remain:

```text
src/gateway/       HTTP routing, authentication, validation, SSE transport
src/activity/      durable structured activity events and read projections
src/commands/      shared command handlers used by gateway, IM, and CLI
workbench/         browser application; no database or process access
```

The gateway may depend on application services. Application services must not depend on the gateway or browser UI.

## Core user journeys

### Desktop start, mobile approval

1. The user selects a project in the workbench.
2. The user enters a requirement and chooses `Claude Build / Codex Review` with the `careful` preset.
3. AgentDock creates the task, prepares its worktree, starts the run, and enqueues it through one command path.
4. The workbench shows the plan and approval request.
5. The user approves from Telegram or Feishu.
6. The workbench immediately reflects the approval and subsequent execution.

### Mobile start, desktop observation

1. The user creates and starts a task from IM.
2. The task appears in the workbench without a browser refresh.
3. The workbench shows which provider is implementing, verification output, review findings, and the fix loop.
4. The user can stop or revise the task from the workbench.
5. IM receives the corresponding state change and terminal notification.

### Reverse provider direction

1. The user selects `Codex Build / Claude Review`.
2. Codex implements in the isolated task worktree.
3. Deterministic verification runs.
4. Claude reviews the diff.
5. If review requests changes, Codex fixes them within the configured review-round bound.
6. Verification and final review complete before the task succeeds.

## Milestone 1 — Local Gateway and Activity Stream

### Goal

Expose the existing durable task model through a safe local API without creating a second execution path.

### Deliverables

- Start the gateway as part of `agentdock serve` when enabled.
- Bind to `127.0.0.1` by default.
- Add a local access token and same-origin checks.
- Add schema validation for every request and response boundary.
- Add shared command handlers so CLI, IM, and HTTP use the same atomic domain operations.
- Add a durable, ordered activity event record for state changes that the UI must replay.
- Add an SSE endpoint with event IDs and reconnect support.
- Add log-tail endpoints backed by artifact files.

### Proposed read endpoints

These routes are a draft contract. Implementation may rename them, but it must preserve the resource and command boundaries.

```text
GET /api/v1/projects
GET /api/v1/providers
GET /api/v1/workflow-presets
GET /api/v1/tasks?projectId=&state=
GET /api/v1/tasks/:taskId
GET /api/v1/tasks/:taskId/diff
GET /api/v1/tasks/:taskId/artifacts
GET /api/v1/runs/:runId
GET /api/v1/steps/:stepRunId/log?offset=&limit=
GET /api/v1/events
```

### Proposed command endpoints

```text
POST /api/v1/tasks
POST /api/v1/tasks/:taskId/prepare
POST /api/v1/tasks/:taskId/revisions
POST /api/v1/tasks/:taskId/runs
POST /api/v1/runs/:runId/approve
POST /api/v1/runs/:runId/reject
POST /api/v1/runs/:runId/cancel
POST /api/v1/runs/:runId/retry
```

`POST /api/v1/tasks/:taskId/runs` must perform the same start-and-enqueue operation used by the orchestrator protocol. The gateway must not call `WorkflowEngine.execute()` directly.

### Activity event contract

Minimum structured events:

```text
task.created
task.revised
task.prepared
task.cancel-requested
task.succeeded
task.failed
task.cancelled
run.queued
run.running
run.paused
run.succeeded
run.failed
run.cancelled
step.started
step.succeeded
step.failed
step.cancelled
approval.requested
approval.decided
review.completed
verify.completed
artifact.created
```

Each event must include:

- a monotonic event ID;
- event type and timestamp;
- task ID;
- optional run and step IDs;
- actor source when caused by a command;
- a compact, versioned payload.

Live `step.output` notifications may be transient. Reconnect must recover output from an artifact file using a byte offset rather than replaying every chunk from SQLite.

### Acceptance criteria

1. A task created through CLI or IM is visible through the API.
2. Start, approve, reject, and cancel requests pass through orchestrator-owned command paths.
3. Repeating a mutating request with the same idempotency key does not create a second run or decision.
4. An SSE client reconnects from its last event ID without losing durable state changes.
5. Restarting AgentDock preserves task/run history and the event cursor.
6. Slow or disconnected clients cannot block workflow execution.

## Milestone 2 — Read-Only Desktop Workbench

### Goal

Make every active and historical workflow understandable from one desktop screen before adding write controls.

### Recommended stack

- React
- TypeScript
- Vite
- static assets served by AgentDock in production

The choice is intentionally conventional. V1.1 does not need server-side rendering or a separate frontend deployment.

### Required views

#### Project and task list

- project status and concurrency limit;
- tasks grouped or filtered by lifecycle state;
- current revision, branch, active run, updated time, and attention state;
- clear badges for awaiting approval, failed verification, review findings, and cancellation.

#### Run detail

- ordered step timeline;
- step type, role, provider, state, duration, and retry/review round;
- live output with bounded buffering and virtualization;
- deterministic verification result separated from LLM review;
- structured review findings with severity and file/line location;
- Git diff by file;
- artifacts and historical task revisions;
- audit/activity timeline showing the command source.

### Acceptance criteria

1. A task created from Telegram or Feishu appears without a manual refresh.
2. Refreshing the browser during an active run reconstructs the same run and step state.
3. The user can answer: who is implementing, who is reviewing, what is running now, why a fix started, and what still needs approval.
4. Large logs and diffs remain usable without loading their full contents into browser memory.
5. The read-only workbench cannot mutate SQLite or start processes through hidden client-side paths.

## Milestone 3 — Task Composer and Desktop Controls

### Goal

Start and control real cross-provider workflows from the desktop while preserving the same safety and scheduling rules as IM and CLI.

### Task composer

Required inputs:

- project;
- requirement text;
- workflow preset;
- provider assignment for `PLAN`, `IMPLEMENT`, `REVIEW`, `FIX`, and `FINAL_REVIEW`;
- maximum review rounds;
- effective project permission profile, shown clearly;
- optional scheduling and priority values already supported by the orchestrator.

The permission profile remains a project policy. The composer may display it and link to project settings, but a run must not silently weaken it.

### Quick provider combinations

- `Claude Build / Codex Review`
- `Codex Build / Claude Review`
- `All Claude`
- `All Codex`
- `Custom`

Quick combinations are UI presets over per-step provider assignments, not new workflow types.

### Required controls

- create and prepare a task;
- start a run;
- approve or reject an approval gate;
- request cancellation;
- retry a failed run where the domain contract permits it;
- add a follow-up requirement as a new `TaskRevision` and run it;
- start a new run with implementer/reviewer assignments swapped.

### Command contract

Every mutation must include:

- an idempotency key;
- authenticated actor/source metadata;
- the expected task revision or run state where concurrent decisions matter;
- a structured payload that never becomes a shell string.

State conflicts must return an explicit conflict response. The UI must refresh the affected resource instead of pretending the stale command succeeded.

### Acceptance criteria

1. The desktop completes a real `Claude Build / Codex Review` workflow.
2. The desktop completes a real `Codex Build / Claude Review` workflow.
3. Repeated clicks or network retries do not duplicate tasks, runs, approvals, or cancellations.
4. Desktop execution obeys project `PAUSED`/`DISABLED`, schedule, global/project concurrency, lease, timeout, and sandbox rules.
5. Revising a requirement creates a new immutable revision and preserves prior runs.

## Milestone 4 — Cross-Channel Continuity

### Goal

Make desktop and phone feel like two views of one workbench rather than separate integrations.

### IM changes

- allow provider assignments when starting a run;
- add a provider-list command;
- keep status, diff, approve, reject, and stop behavior consistent with desktop commands;
- include direct task/run identifiers in approval and terminal messages;
- notify subscribed conversations about approval requests, terminal state, cancellation, and timeout;
- display the command source in audit/activity views.

Exact IM syntax may vary by adapter, but both adapters must create the same domain command. A possible compact form is:

```text
/run TASK_ID cross-review IMPLEMENT=claude REVIEW=codex FIX=claude FINAL_REVIEW=codex
```

### Cross-channel rules

1. A task belongs to AgentDock, not a browser tab or IM conversation.
2. Any authorized surface may observe the task.
3. Any authorized surface may issue a valid command.
4. The first valid approval/rejection wins; concurrent stale decisions receive a conflict result.
5. Notifications follow explicit task subscriptions and never cross Telegram/Feishu conversation identities accidentally.
6. A surface reconnects from durable state instead of relying on its local message history.

### Acceptance criteria

1. Start on desktop, approve on phone, observe completion on desktop.
2. Start on phone, inspect live progress and diff on desktop.
3. Stop on desktop and receive the cancellation result on the subscribed IM conversation.
4. A Telegram-created task is visible and controllable from Feishu and desktop, subject to authorization.
5. Simultaneous desktop and IM approval attempts produce one durable decision and no duplicate execution.

## Milestone 5 — Security, Stability, and Release

### Goal

Make the workbench safe for daily local use and verify that the new UI does not weaken V1.0 guarantees.

### Security requirements

- bind locally by default;
- require a generated local access token;
- enforce same-origin and reject arbitrary CORS access;
- validate every path, query, and JSON payload;
- redact secrets from API responses, events, logs, errors, and browser diagnostics;
- never expose agent or IM credentials to frontend code;
- stream artifacts only through validated task/artifact ownership checks;
- keep process execution as argv arrays with shell disabled;
- record all mutating actions in the audit log.

### Reliability and resource requirements

- cap SSE connections, pending bytes, and per-client buffering;
- disconnect slow clients without affecting agents;
- bound in-memory log buffers and virtualize rendered output;
- paginate or stream large diffs and artifacts;
- preserve event ordering across concurrent desktop and IM commands;
- tolerate browser refresh, laptop sleep, temporary network loss, and AgentDock restart;
- ensure shutdown waits for gateway cleanup without weakening orchestrator process cancellation.

### Test requirements

- unit tests for validation, authentication, idempotency, event ordering, and state conflicts;
- command contract tests proving HTTP, IM, and CLI call the same application operations;
- concurrency tests for simultaneous desktop/IM approval, cancel, and revision commands;
- reconnect tests for SSE cursors and log offsets;
- API tests for project/task/run/diff/artifact reads;
- Playwright end-to-end tests for the workbench;
- macOS and Linux CI coverage;
- one real bidirectional Claude/Codex acceptance run before release.

### Acceptance criteria

1. No API response or browser event contains provider, GitHub, Telegram, or Feishu credentials.
2. A disconnected or maliciously slow browser cannot stall the orchestrator.
3. Concurrent commands converge on one valid durable state.
4. The complete deterministic test suite, typecheck, UI end-to-end suite, and diff checks pass on macOS and Linux.
5. The release checklist records one real workflow in each provider direction.

## V1.1 end-to-end acceptance

V1.1 is complete only when all scenarios pass:

1. Desktop starts Claude implementation with Codex review.
2. Codex reports a blocking finding, Claude fixes it, verification passes, and Codex final review passes.
3. Desktop starts Codex implementation with Claude review and completes the reverse path.
4. Desktop starts a `careful` run and phone IM approves both gates.
5. Phone IM starts a run and desktop shows its live steps and output.
6. Desktop cancels a long agent or VERIFY process and the process tree terminates under the existing cancellation contract.
7. Browser reconnect resumes from durable event state and the correct log offset.
8. AgentDock restart preserves task history and applies the existing orphan-recovery contract.
9. Concurrent desktop and IM commands remain idempotent and do not create duplicate execution.
10. Security inspection confirms no provider or IM secret reaches the browser, agent worktree, verification process, or logs outside its existing authorized boundary.

## Implementation order

Implement in this order:

1. Local Gateway and Activity Stream
2. Read-Only Desktop Workbench
3. Task Composer and Desktop Controls
4. Cross-Channel Continuity
5. Security, Stability, and Release

Do not begin with the composer. A trustworthy read model and reconnect contract must exist before the UI can safely mutate workflows.

Each milestone should land independently with its own tests and acceptance evidence. Do not combine the entire V1.1 scope into one unreviewable change.

## Definition of done

V1.1 is done when:

- the browser and both IM adapters operate the same durable task model;
- Claude/Codex roles can be swapped without changing workflow code;
- all execution enters through orchestrator-owned scheduling and safety gates;
- task state, structured findings, verification, diffs, artifacts, and logs are understandable from the desktop;
- approvals, revisions, retries, and cancellation are safe under concurrent surfaces;
- refresh and restart do not lose durable history;
- the new local API does not expose secrets or create a remote attack surface by default;
- all end-to-end acceptance scenarios have recorded evidence.

## Deferred after V1.1

Reconsider these only after daily usage shows a concrete need:

- native desktop wrapper;
- richer mobile UI;
- generic direct agent chat;
- visual workflow builder;
- automatic task/provider routing;
- more providers and IM adapters;
- multi-machine workers;
- team accounts, RBAC, and hosted deployment;
- task dependency DAGs and scheduled autonomous work.
